# Jumpbox Kiosk Project

## 1. The Goal
The primary objective of this project is to create a secure, stateless hardware terminal by PXE booting a completely diskless device. This device automatically connects to a persistent, remote jumpbox (e.g., hosted on a Proxmox LXC container). By removing local storage and relying on a read-only live OS, local persistence is eliminated, ensuring a clean, secure environment upon every reboot.

## 2. Common Challenges Addressed
Building a reliable PXE kiosk environment often presents several significant challenges:

*   **Missing Network Drivers:** Standard live OS images (like Porteus) often strip out kernel modules to save space, omitting necessary network drivers (e.g., Realtek) required by target hardware, preventing post-boot connectivity.
*   **STP Delays on Switches:** Spanning Tree Protocol (STP) on network switches can cause a standard ~30-second delay while the port transitions to a forwarding state. This frequently results in DHCP timeouts during the crucial early PXE boot phase.
*   **Nginx 502 Errors:** When attempting to route remote desktop traffic (like KasmVNC) through an Nginx reverse proxy, 502 Bad Gateway errors can occur due to WebSocket proxying misconfigurations and backend connection failures.
*   **Authentication Conflicts:** Default remote desktop authentication mechanisms can clash with the goal of a zero-touch, automated kiosk login, requiring adjustments to bypass login prompts seamlessly while maintaining security.

## 3. The Solution
To overcome the limitations of pre-built live environments, this project uses a **custom Debian Live Kiosk ISO**. 

Using Debian `live-build`, a tailored OS image is crafted that explicitly includes required dependencies (such as `firmware-realtek`). This custom build hardens the X11 environment (disabling VT switching), configures LightDM for automatic login, and launches Openbox as a lightweight window manager. Openbox immediately executes a supervised script that continuously forces a fullscreen Firefox ESR instance directed at the remote jumpbox URL (e.g., `https://<YOUR_JUMPBOX_URL>`). To mitigate STP delays, retry loops and increased timeout values are integrated into the network configuration phase of the boot process.

## 4. Configuration Instructions

### Jumpbox (e.g., Proxmox LXC) with KasmVNC
The core remote environment is hosted on a container or virtual machine.
1.  **OS:** Debian/Ubuntu-based container.
2.  **KasmVNC:** Installed to provide a high-performance web-based desktop. It serves the desktop interface directly over HTTPS/WSS.
3.  **Reverse Proxy (Optional):** Nginx can be used to handle SSL termination. Ensure WebSocket support is correctly configured to prevent 502 errors.
4.  **Desktop Environment:** A lightweight DE (e.g., XFCE) runs inside the container, which the user interacts with via the browser on the diskless device.

### iVentoy PXE Server
The network boot process is driven by a PXE server like iVentoy.
1.  **Deployment:** iVentoy runs on a dedicated machine or container to handle DHCP/TFTP duties.
2.  **ISO Hosting:** The custom `live-image-amd64.hybrid.iso` generated by the build scripts is placed in iVentoy's `iso` directory.
3.  **Boot Process:** The device fetches the bootloader via TFTP, then loads the Debian Live ISO directly into RAM over HTTP, booting seamlessly into the KasmVNC session.
